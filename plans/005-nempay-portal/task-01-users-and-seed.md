# Task 01 — Portal users table + multi-merchant seed

**Plan:** ./plan.md · **Depends on:** none · **Blocks:** task-02, task-04

## Context
- Spec acceptance criteria covered: **AC1** (a user to authenticate as), **AC2** (two merchants so
  isolation is testable), **AC3** (a user is tied to exactly one merchant).
- Links: nem_pay/CLAUDE.md ("portal" auth = JWT sessions); 0003_merchants_api_keys schema; devseed.

## Requirements
- A `users` table: one login identity, bound to exactly one merchant, with a bcrypt password hash.
- Dev seed provisions a **second** merchant and one user per merchant, so a signed-in user of A can
  be tested against data owned by B. Idempotent, dev-only (guarded by `NEMPAY_DEV_SEED`).
- Passwords are never stored in plaintext; the raw dev password is printed on boot like the dev keys.

## Files to create / modify
```
nem_pay/api/db/migrations/0007_portal_users.up.sql      (new)
nem_pay/api/db/migrations/0007_portal_users.down.sql    (new)
nem_pay/api/db/queries/users.sql                        (new: GetUserByEmail, InsertUser)
nem_pay/api/internal/repository/db/*                     (regenerated by sqlc)
nem_pay/api/internal/devseed/devseed.go                 (seed 2nd merchant + users)
```

## Implementation steps
1. Migration `0007`: `users(id uuid pk, merchant_id uuid not null references merchants(id),
   email text not null unique, password_hash text not null, created_at timestamptz default now())`.
   Down drops the table.
2. Queries: `GetUserByEmail` (returns id, merchant_id, email, password_hash) and `InsertUser`.
   Run `make sqlc` to regenerate the typed repository.
3. Devseed: keep the existing dev merchant + keys; additionally upsert a **second** merchant at a
   fixed uuid, and one user per merchant (fixed emails, e.g. `owner@merchant-a.test` /
   `owner@merchant-b.test`) with bcrypt-hashed known dev passwords. Idempotent (insert only if the
   email is absent). Log the seeded emails + dev password with the same "dev only" warning.
4. Do **not** wire auth yet (task-02) — this task only lands the data + seed.

## Validation / tests
- `make test-db` migrates cleanly up and down (0007 applies and rolls back).
- A devseed unit/integration test asserts: after `Run`, both merchants exist, each has exactly one
  user, `password_hash` verifies against the known dev password via bcrypt, and a second `Run` is a
  no-op (idempotent). Proves the data foundation for **AC2/AC3**.

## Risks & rollback
- Risk: seeding predictable credentials outside dev. Mitigation: gated by `NEMPAY_DEV_SEED`, same as
  the existing key seed; warning logged.
- Rollback: `0007_portal_users.down.sql` drops the table; revert devseed additions. No money tables
  touched.
